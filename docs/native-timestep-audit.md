# Focused native timestep audit

This is a source audit of the Build 70 foundation, not a physics acceptance result. The archive adaptation is implemented in Build 73; its native gameplay acceptance remains pending. Other proposed changes under `staged/timestep/` are unapplied and require review, native contract execution, compilation, and loaded-map gameplay evidence. Production sources remain frozen during current live timing tests.

The authoritative path is `SV_FrameInternal` in `engine/src/server_mp/sv_main_mp.cpp:1231`: each fixed step calls the actual command consumer, `SV_RunFrame`, and `SV_PostFrame`. `G_RunFrame` in `engine/src/game_mp/g_main_mp.cpp:1233` derives `level.frametime` from the two authoritative timestamps; its entity dispatcher invokes each live entity once per frame. At the custom 1 ms rate, a literal that represented one old server frame must be distinguished from a real 50 ms gameplay interval, spatial tolerance, or sampling policy.

## Live multiplayer sites that need work

### Dropped items: coupled future sweep, contact trajectory, and support probe

`G_RunItem`, `engine/src/game/g_items.cpp:1300`, evaluates the trajectory at `level.time + 50` at line 1367. On collision it publishes a `TR_LINEAR_STOP` segment with duration 50 at line 1421 and derives velocity from displacement multiplied by 20 at line 1426. Those three values describe the same old 50 ms step. The function also changes the actual sweep endpoint downward by one unit when squared displacement is below 0.1 at lines 1388–1390, then commits that endpoint on a clear trace at lines 1400–1403.

The extra down unit is a spatial support check embedded in motion. At a 1 ms interval, sufficiently slow movement triggers it repeatedly; substituting `+1` alone retains that artifact. For an analytic gravity trajectory already sampled every millisecond, the old future horizon also places collision and linked item poses 50 ms ahead of the authoritative timestamp. A fresh gravity transition initializes `trTime = level.time`, so the old first evaluation advances a whole 50 ms immediately.

The staged proposal preserves the function's existing one-step-ahead convention but makes that step the actual positive frame interval. Duration and reciprocal conversion change together. It traces the physical motion endpoint first; a small-motion support check is a separate one-unit trace from that endpoint. Only an immediate supporting contact (fraction below the native 0.01 tolerance and positive ground normal) can take the existing settle/orient/ground path. A missed or more distant support probe never becomes committed falling motion. Existing primary collision clipping, owner exclusion, item mask, sky removal, and think ordering remain in place. At 50 ms, ordinary gravity and contact segment endpoints are the comparison baseline; the original low-motion down-unit artifact is deliberately corrected rather than claimed identical.

Required native follow-up: dropped weapons with zero/slow lateral velocity, airborne free fall, wall glancing, stairs/slopes, ground within and outside support slop, starts inside geometry, moving ground entities, sky removal, item pickup/touch, and snapshot interpolation. Trace fixture tests below establish control-flow contracts, not loaded BSP correctness. Contact resets and moving-platform semantics deserve explicit observation before promoting this change.

### Multiplayer helicopter dispatch disagrees with its integration interval

`G_VehicleFrameMsec` / `G_VehicleFrameSeconds`, `engine/src/game/g_helicopter.cpp:14`, now return the actual frame interval under `COD4X1KHZ`. Native helicopter velocity, rotation, position, collision, jitter integration, and damping use that helper. Shared `Scr_Vehicle_Think`, `engine/src/game/g_scr_vehicle.cpp:675`, dispatches `VEH_UpdateAIMove` or `VEH_UpdateClientChopper`, updates native position and aim, and schedules its next think with that helper at line 753.

However, `Helicopter_Think`, `engine/src/game_mp/g_scr_helicopter.cpp:516`, overwrites the next deadline with `level.time + 50` at line 519. Spawn and first-think initialization use the same 50 ms deadline at lines 389 and 428. Therefore these physics paths can integrate 1 ms only once every 50 ms. This is a concrete dispatch/integration mismatch, not just an unexplained literal. The staged proposal schedules those three entries with `G_VehicleFrameMsec()`. Script reaction, target acquisition, jitter periods, and weapon duration values are not globally changed.

Important branch distinction: `Scr_Vehicle_Think` calls `VEH_UpdateWeapon` only in its `KISAK_SP` branch. The actual MP vehicle turret update instead runs from `G_VehEntHandler_Think`, `engine/src/game_mp/g_vehicles_mp.cpp:804`; that path already reschedules with the frame helper and `VEH_UpdateWeapon` subtracts `level.frametime` at `game/g_scr_vehicle.cpp:6168`. The staged contract verifies that MP turret countdown remains elapsed-time based; it does not invent a helicopter-to-turret call. Ordinary MP stationary turret think, sound, and fire time already use `TurretStepMsec` / `TurretThinkMsec` in `game_mp/g_misc_mp.cpp:15`.

Required native follow-up: helicopter killstreak scripts and client-controlled chopper where assets expose it, position/rotation/acceleration limits over equal elapsed time, collision slide and look-ahead behavior, aim updates, jitter RNG cadence, damage/touches, and vehicle turret fire cadence. Advancing physics more frequently must not multiply RNG draws for a seconds-based decision.

### Javelin turn drag still applies a stock retention once per call

`JavelinRotateVelocity`, `engine/src/game/g_missile.cpp:2481`, already scales climb/descent acceleration by `MissileStepSeconds`, and `JavelinRotateDir` limits rotation using that interval at line 2529. But line 2507 applies `(1 - turnDiff / 180 * missileJavTurnDecel) * speed` once per update. In the limited-turn branch, `turnDiff` is the full pre-limit directional-error estimate returned at line 2548; it is not the tiny rotation actually made during this 1 ms tick. The retention can consequently be applied 1,000 times per second instead of 20.

The staged proposal interprets the existing retention as a 50 ms tuning value and applies `pow(retention, dt / 0.05)` only to the custom path. It preserves the exact original arithmetic when `dt` is 50 ms. The registered deceleration domain is [0, 1] (`game/g_missile.cpp:209`); the native directional-error estimate is bounded by 180 for valid normalized inputs, so zero retention can remain zero without inventing a new clamp. The proposal does not change direction selection, turn caps, speed limits, stage changes, or acceleration tuning. This is a defensible stock-rate retention conversion, but a live target-turn fixture must settle whether stock intent instead requires drag proportional to actual rotated angle. The two alternatives must not be silently conflated.

Required native follow-up: identical top/direct attack paths against stationary and moving targets, ascent/descent, sharp/near-zero turns, default and boundary deceleration values, launch velocity, proximity and impact behavior. Deterministic controlled-turn tests isolate damping arithmetic and cannot attest the full guidance solver.

### Other concrete unresolved items

- `game/g_missile.cpp:276`: an airborne smoke grenade retry writes the absolute deadline `nextthink = 50`. `G_RunThink` (`game_mp/g_main_mp.cpp:1163`) tests positive deadlines against `level.time`, clears them, and then invokes the handler. After time 50 this retry is already due on every server tick. If the intent is a 50 ms landing poll, use `level.time + 50`, preserving the actual 60,000 ms timeout, rather than changing the poll duration to 1 ms. This likely predates the custom rate; verify grenade detonation-on-ground semantics before repair.
- `game/g_missile.cpp:2308` and `:2353`: vertical steering converts desired-minus-current velocity to acceleration with `*20`, while the eventual integration at `:2143` now uses `dt`. It could be an implicit reciprocal stock frame interval or a tuned 50 ms feedback response. The attraction path already uses error divided by `dt` at `:1976`, but that is not proof of identical steering intent. Compare capped and uncapped stock steering before choosing `error/dt` or an explicitly preserved feedback time constant.
- `game_mp/g_player_corpse_mp.cpp:108`: corpse root motion is discarded unless `Vec3LengthSq(deltaChange) > 1.0` during the current server animation step. `XAnimCalcDelta` uses previous/current animation times, while server XAnim now advances with actual `level.frametime` (`game_mp/g_utils_mp.cpp:920`). A root motion delta below one unit per millisecond can be lost instead of accumulated. Preserve fractional root motion and separate a distance-based collision/support threshold from the clock; first validate corpse root deltas, settling, animation notifies, and ragdoll mode. No corpse proposal is applied here.
- `server_mp/sv_snapshot_mp.cpp:2039–2070`: `SV_SendClientMessages` appends a native archive each authoritative frame, retaining 1,200 frame descriptors and a bounded byte ring. `SV_GetCachedSnapshot` at `:704–715` indexes by `sv_fps`. At 1,000 Hz the descriptor horizon is 1.2 seconds rather than the old 60 seconds at 20 Hz, with potentially earlier byte eviction. The 50 ms fallback decrement in `game_mp/g_active_mp.cpp:951` is a search step, not a killcam clock integrator. Retain a separate timestamped, bounded killcam/archive policy or deliberately sample presentation archive at its own interval with timestamp-based lookup; do not enlarge everything 50 times or substitute a 1 ms linear search. Hit rewind and snapshot baseline history are different domains.
- `server_mp/sv_snapshot_mp.cpp:1992–2029`: optional average-BPS diagnostics count 20 frames, sum a frame-byte window, and report every 20 calls. At 1 kHz those legacy diagnostics no longer describe a one-second stock window. Prefer elapsed-time accounting; this is telemetry, not a physics change.

## Values that should not be blindly replaced

- `game_mp/g_trigger_mp.cpp:193` retains 50 ms ordinary hurt-trigger cooldown and a 1,000 ms flagged cooldown. Its damage amount is unchanged; replacing 50 with 1 raises damage-per-second roughly fiftyfold. Preserve the seconds-based stock damage interval while checking contact at 1 kHz.
- `game_mp/g_active_mp.cpp:771` sets a player entity `TR_LINEAR_STOP` extrapolation limit of 50 ms. This bounds a published trajectory during missing updates, rather than driving player physics. A loss/reordering fixture and explicit extrapolation policy must precede changing it; a 1 ms limit can freeze remote entities on one missing packet.
- `bgame/bg_animation_mp.cpp:538`, `:666`, `:688` add a 50 ms animation timer grace; replacement is paired with `torsoTimer < 50` / `legsTimer < 50` at `:545` / `:580`. This is an animation transition policy. Preserve it until native animation duration and transition tests establish the desired stock timing.
- `bgame/bg_animation_mp.cpp:2093` uses `angleError * 0.05` as a response gain, then multiplies angular movement by actual `bgs->frametime` at `:2098` / `:2113`. The gain is not a timestep. Similar 20/50 constants in stance heights, ladder pushes, mantle geometry, and velocity thresholds represent units or tuning.
- `bgame/bg_pmove.cpp:1800`, acceleration/friction/gravity in `bg_pmove` and `bg_slidemove`, and weapon time/delay/breath updates in `bgame/bg_weapons.cpp:2338`, `:2405`, `:1543` use native milliseconds or seconds already. Existing fractional bob/idle phases are preserved by the custom helpers. This static review is not a proof that every discretization or low-speed threshold is solved.
- `game/g_mover.cpp:299–369` evaluates the analytic position/angular trajectory at authoritative `level.time`; blocked rollback shifts `trTime` by `level.time - level.previousTime`. These mover durations already have elapsed-time semantics. `game/g_scr_mover.cpp:249` has a one-millisecond positive duration floor rather than a 50 ms quantizer.
- Missile bounce speed retention is triggered by collisions, not every tick. Do not exponentiate an event response solely because it contains a fractional multiplier. Destabilization RNG at `game/g_missile.cpp:1814–1837` already draws according to a stored seconds-based deadline; retain that interval.

## Excluded single-player and debug literals

- `game/g_vehicle_path.cpp:1178` advances a path sample by `speed * 0.05`. The live `VEH_UpdatePath` call in shared `game/g_scr_vehicle.cpp:696–702` is `KISAK_SP` only. `VP_DrawPath` also samples this helper on local debug copies (`game/g_vehicle_path.cpp:1563`). Changing its sample length globally would alter a bounded debug draw loop and deferred SP path interpolation. It is not an established current MP simulation defect.
- `game/g_scr_vehicle.cpp:6104` decrements a vehicle weapon timer by 50 only inside `KISAK_SP`; the MP branch is elapsed-time based as described above.
- `game/turret.cpp` and `game/g_animscripted.cpp` begin with an explicit single-player-only compile guard. Their `0.05` rotation/movement steps and 50 ms deadlines are later SP work, not the active MP turret implementation.
- `G_PredictMissile`, `game/g_missile.cpp:3239`, is a coarse predictive sampler starting at `level.time - 50`, advancing by 50 ms, and reconstructing a fractional hit time using that sample interval. The only found native caller is SP `actor_grenade.cpp:915`. It is not the authoritative `G_RunMissile` step. Replacing its sample interval with 1 ms without an accuracy/cost contract would add roughly fifty times the prediction trace work.

## Staged proposals and contract scope

`staged/timestep/proposals.py` defines exact, guarded transformations for only item motion/probe, the three MP helicopter deadlines, and custom Javelin retention. It can emit review patches under that staged directory and never writes engine inputs. The native extraction harness below exercises its transformations. The three production changes remain unapplied.

The expanded extraction contracts also pass: [current result](../staged/timestep/results/20261003-125022-040380/result.json). Added cases execute the actual starts-solid and two-trace wall-slide branches, ownerless traces, moving versus stationary ground, and changing controlled turn-error sequences. These dependency fixtures still do not prove real BSP contacts, full missile guidance or authoritative replay.

The first harness at `staged/timestep/run_native_contracts.py` with `contracts_driver.cpp` passes 232 assertions and three legacy negative controls using MSVC Win32 Release. [Exact source, commands and results](../staged/timestep/results/20261003-124123-037777/result.json) are retained. It extracts the actual `G_RunItem`, `BG_EvaluateTrajectory`, `G_SetOrigin`, `Helicopter_Think`, `G_VehicleFrameMsec` / `G_VehicleFrameSeconds`, MP `VEH_UpdateWeapon`, and `JavelinRotateVelocity` bodies from current and proposed source. The exact three helicopter substitutions are enrolled by guarded transformation; spawn initialization remains source enrollment. Dependency structures and trace/guidance/vehicle callbacks are synthetic, so these contracts cannot attest native ABI, BSP collision, full helicopter integration, VM execution, target selection or whole-world replay. Cases cover independent support versus committed motion, trajectory/contact duration coupling, elapsed helicopter/turret deadlines and turn retention. Starts-solid/wall-slide detail, moving ground, actual notifications and complete guidance remain additional work. The brace scanner ignores comments and literals and refuses ambiguous definitions or drifted anchors. Generated source/binaries stay under staged result directories; no engine input is changed.

Planned item contracts: an open analytic gravity trajectory at 1/2/8/50 ms; equal one-second gravity endpoints at 50 ms between current/proposed source; small lateral motion with a missed support probe preserving height; support within versus outside the native immediate-contact tolerance; positive slope versus vertical-wall support normal; primary wall hit publishing a segment whose duration and velocity reproduce the exact endpoint; primary starts-solid behavior; owner exclusion and item trace mask for both queries; sky/free and link/think/orient ordering. Probe coordinates and actual committed coordinates must be observed separately. The legacy function should reproduce the unwanted down-unit behavior as a negative control, rather than using that behavior as the candidate acceptance expectation.

Planned helicopter contracts: dispatch the extracted `Helicopter_Think` from `nextthink` over a real simulated one-second owner timeline, using the extracted dt helper. A dependency fixture records calls and elapsed dt, so the current 50 ms overwrite visibly schedules only 20 one-millisecond integrations while the proposed path schedules 1,000. This proves the deadline/helper coupling, not the complete native acceleration graph. Separately execute the actual MP `VEH_UpdateWeapon` branch with held versus released attack, fixed native weapon duration, zero/positive countdown, and equal elapsed time; the current and proposed sources must remain identical because no turret countdown change is proposed. Do not wire this weapon fixture into `Scr_Vehicle_Think`, whose call is SP-only.

Planned Javelin contracts: use the actual `JavelinRotateVelocity` with controlled native turn-result dependencies, covering zero, 15, 30, 45, 90, and 180 degree-error estimates; native deceleration boundaries 0 and 1 plus its default; climb/descent speed caps; constant and changing turn error over equal elapsed time; repeated 1/2/8 ms updates against the same stock 50 ms retention intervals. Compare exact original arithmetic at 50 ms and float-tolerant accumulated retention at 1 ms. The current per-call damping must fail the rate-invariance negative control. These controlled results isolate retention and do not prove the full target-selection or direction solver.

Native function extraction will keep the contracts from testing a separate rewrite of the changed algorithm. Their dependency fixtures remain intentionally incomplete: no real BSP, script VM, DObj, server replay restore, renderer, real helicopter acceleration graph, missile target selection, or actual firing will be attested.

Integration order after the current matrix: review and run extracted contracts; add loaded-map fixtures that use actual native item/vehicle/missile functions and collect typed state; apply one coherent change at a time; compile both targets; rerun lifecycle and short performance cases; retain unresolved corpse/steering/killcam gates explicitly. A 1 kHz tick count or a pure contract pass alone does not establish stock gameplay equivalence.

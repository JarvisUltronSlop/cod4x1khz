The integration wires `native/steam_identity_format.hpp` into the two public host exports and `sdk/tests/native_identity_format_probe.inc` into the rebuilt regression DLL. Build 71 passes the standalone formatter suite and [actual loaded-DLL fresh-default/configured-zero fixture](../results/plugin-identity-format-native-20261003-064911-596900/result.json). The reviewed [two per-export proofs](evidence/build71-sdk-identity-format/index.json) are published; dvar saved-config persistence remains partial. Historical artifacts are preserved. `config/staged/steam-identity-format.patch` records the original integration patch before the fixture-only twenty-command repair.

Pinned `upstream/cod4x_server/src/sapi.c:24` requires an empty result for every positive `Plugin_SteamIDTo64String` capacity below 20. At line 316, `Plugin_SteamIDToString` selects its representation using `sv_usesteam64id`; that dvar is registered true at line 759. The former public wrappers always selected Steam3 for the configurable function and used generic truncation for the explicit decimal function. The integrated source corrects both contract gaps.

The new pure helper requires 20 bytes for decimal mode, counts digits without allocation, and copies only a whole number plus its terminator. A value with twenty digits requires twenty-one bytes. A capacity-20 request for that value produces an empty result rather than reproducing the pinned unchecked `sprintf` overflow. Positive rejected buffers change only byte zero; zero/negative lengths and null pointers are untouched. Steam3 retains allowed universe/type checks, pinned account-type spelling and bounded terminated truncation. The helper takes the configured boolean explicitly and performs no global/dvar/provider access.

## Integrated production behavior and build requirements

- The owned native SDK implementation includes `<steam_identity_format.hpp>`; `Plugin_SteamIDTo64String` calls `khz::identity_format::Steam64` with its existing public void signature.
- `Plugin_SteamIDToString` copies `sv_usesteam64id` under the existing `KHZ_DvarScope`, then formats outside the scope. Existing public Cvar getters use the same synchronization. An absent dvar returns false, preserving pinned null-dvar Steam3 behavior.
- Administration registers `sv_usesteam64id` with true as its default and preserves explicitly configured/archived values. Fresh-default verification needs an empty isolated benchmark home and no setting overriding this dvar. The bootstrap chooses `runtime/benchmarks/server-<port>` from the server port; an arbitrary `fs_homepath` override does not establish a fresh bootstrap home.
- The old `native_stats_probe.inc::identity_probe` expectation follows its configured mode. Decimal mode verifies that the three-byte refusal clears byte zero and leaves the remaining bytes untouched; Steam3 verifies bounded termination. Its existing GUID/conversion assertions remain intact.
- The regression DLL includes the new C `.inc` and invokes it through the existing `khz_fixture_identity format` command at power 100, preserving the pinned twenty-command limit. The standalone C++17 test uses the `native/` include path and needs no engine, Windows, network or provider libraries.

## Actual verification scope

The standalone file stages guard-byte tests over capacities -2 through 64, null pointers, ordinary 17/19-digit identifiers, the 19-to-20-digit transition, `UINT64_MAX`, both configured formats, all ten printable account types and invalid universe/type outputs. It does not assert that a numeric identifier is authenticated.

The C fixture calls the real host exports. It contains six independent identifier goldens at capacities -1, 0, 1, 3, 19, 20, 21 and 48 under both dvar settings, checks guard bytes and restores the initial boolean. In each Build 71 phase `KHZ_IDENTITY_FORMAT_SELECTED` passes 99 cases and `KHZ_IDENTITY_FORMAT_EXPLICIT64` passes 96. `KHZ_IDENTITY_FORMAT_STEAM3` passes 128 native checks: every combination of twelve permitted universes and ten printable types at account-id maximum, plus five rejected universes and three rejected types. Null-output calls with positive, zero and negative lengths survive. The native harness verifies fresh default true separately from configured false, binds actual server/DLL/fixture/helper hashes to the coherent archive and proves both exact owned processes exited. These assertions support the two reviewed formatter exports; aggregate conversion markers do not promote other exports.

## Parser safety adaptations to classify explicitly

No parser implementation is changed by this staging. Current `khz_identity.cpp::StringToSteamId` retains valid legacy/Steam3/Steam64 representations and account-type aliases `T`, `c` and `L`. Compared with pinned scanning, it rejects long input rather than parsing a truncated 127-byte prefix; enforces decimal bounds, a 0/1 legacy parity field, non-wrapping account-high bits and a 20-bit instance; and rejects trailing text. These prevent aliases produced by truncation, integer wrap or bits spilling into another field. They are safety adaptations, not proof of an official identity provider.

Current GUID conversion rejects non-hex characters in an otherwise 32-character string; pinned `strtol` turns invalid pairs into zero. Valid 32-hex input must retain the exact pinned salt, PBKDF2-SHA256/100 conversion and existing independently derived golden value. The current parser also accepts the explicit four-field Steam3 instance form; pinned `ParseSteam3ID` scans four fields but its final `cFieldConverted != 3` check rejects that form. Document this as a parser bug fix rather than claiming identical behavior on every pinned malformed or rejected input. Tests must cover these legitimate extensions/refusals before a whole parser contract is promoted.

Default-mode and minimum-capacity fixes have current Build 71 loaded-DLL evidence. A future changed source or binary requires fresh archive-bound verification. The remaining parser/classification/GUID exports need their own complete contract review and native boundary cases.

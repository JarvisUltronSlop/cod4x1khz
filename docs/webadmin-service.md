# Web administration service design

The isolated custom-pair implementation is prepared for the next integration checkpoint, with no verified native endpoint claim yet. The source audit covers pinned CoD4x server `ddd65fc`, especially `src/webadmin.c`, `src/httpftp.c:2021–2515`, and `src/common.c:610–622`. The public source registers `sv_webadmin` but comments out its `HTTPServer_Init` call at startup. Its available web functionality still belongs in the capability inventory; a source function or inactive registration does not establish working parity.

The applicable capabilities are a public `/status` page, `/webadmin` login/logout and authenticated server/player status, the administrator list, a power-checked command console with redirected output, connected-client kick/ban controls, offline identifier bans, and static `/files/` resources from `webadmindata`. `Webadmin_AddAdmin` is a commented stub, so the existing native administration commands supply account management. Identity fields in this custom pair display proven local keys; official Steam authentication remains unavailable rather than being inferred from a submitted identifier.

Implement an isolated `khz_webadmin` module, disabled by default through `sv_webadmin=0`. Its listener should default to `127.0.0.1` and an explicit separate TCP port, with configuration copied before the worker starts. The first native fixtures use only project-owned loopback endpoints. Keep the HTTP request/response parser independent of the engine, bounded to 16 connections, 16 KiB headers, 4 KiB form bodies and 128 KiB responses. Reject conflicting content lengths, unsupported transfer encodings, malformed escapes, oversized requests and connection/pipelining ambiguities. Bound deadlines and response sends; neither slow readers nor password work may block a gameplay tick.

The network worker owns sockets, request framing, form decoding, HTML escaping and response serialization. Publish immutable server/admin views at a modest service cadence, such as 10 Hz, containing copied names, teams, score/ping, provider disposition, full identity and admission serial where authorized. Public status must honor undercover visibility and omit private keys, password hashes and full administrative identity. Static resources come only from a project-confined prepared asset directory, with reparse-point checks and bounded reads on workers; there is no arbitrary filesystem route.

Password derivation runs off the authoritative owner. A login job carries a copied administrator credential record and request generation; a worker runs PBKDF2 verification. The owner checks the live name, power, salt and password hash before admitting a session. `Store::AdmitVerifiedCredential` avoids deriving the password a second time. It issues random bounded session tokens with a one-hour expiry, and account/password policy changes revoke sessions. Failed logins are rate limited per peer and globally without banning unrelated game identities sharing that peer address.

Authentication/session state, policy mutation and engine commands remain on the server owner. The HTTP worker submits copied typed requests through a fixed queue; outer service drains a bounded number and returns immutable completions. Recheck session, current command rule and issuer power immediately before execution. A disconnected client slot must not become a new kick/ban target: structured actions carry the displayed admission serial and full copied subject. Ban persistence and logging retain the original invoker identity/name/power. Offline local-key bans use a full validated fingerprint; Steam conversion alone does not authorize a Steam-provider ban.

Reuse the native command registry and administration implementation for command-console behavior, with exactly one validated command per request and the existing target hierarchy checks. Set and restore an explicit web invoker context rather than treating web requests as console power100. Capture redirected output into a bounded completion outside gameplay ticks, escape it before rendering, and restore context on engine error cleanup. State-changing requests require a session-bound anti-CSRF token and POST; use HttpOnly/SameSite cookies and validate the configured host/origin. Logout invalidates its session. Any later nonloopback deployment needs a separately verified transport configuration rather than a claim of official service compatibility.

Map/error/shutdown barriers cancel old request generations, drain or discard completions, close worker resources and join before filesystem teardown. Existing sessions may survive a map only if policy remains valid; status/actions still use the new server/map/admission generation. Queue fullness and rejected work return explicit HTTP failures and counters rather than allocating unbounded requests. Record maximum service/callback duration and HTTP queue/drop counts alongside 1 kHz telemetry.

The release fixture sequence should remain short and native:

1. Check the disabled default creates no listener; enable a loopback fixture and verify real `/status`, static-resource confinement, escaped game names and 16-slot visibility.
2. Create isolated project administrator credentials, exercise failed/successful login, HttpOnly/SameSite session handling, expiry/logout/password revocation, and bounded slow/malformed clients.
3. Exercise permitted/denied console commands with captured output and correct audit attribution; use two powers and never infer a web issuer from a game slot number.
4. Kick/ban only isolated headless test identities, reuse a displayed slot before action drain, and verify the replacement is unaffected. Check offline full-key bans and persistence in the isolated policy store.
5. Restart/change map and abort requests while network/password jobs run; verify cancellation, bounded memory and no stale completions.
6. Compare a short active 16-player/bot benchmark with and without HTTP load. If server debt grows or tick-work acceptance fails, retain the failure as an explicit release blocker.

Current source components are `native/webadmin_policy.hpp` (HTTP/forms/cookies/origin/static-path rules), `engine/src/khz/khz_webadmin.{h,cpp}` (the bounded socket/password worker and owner request/result queue), and `khz_webadmin_adapter.inl` (the prepared owner policy/command integration). Processing slots cannot be reused until the owner acknowledges completion, including on map/error cancellation. HTTP status defaults to hiding undercover clients; authenticated viewers need power60 to see them. Native bots may be kicked with a matching admission generation but do not become persistent identity-ban subjects.

`tests/webadmin_policy_tests.cpp` and `tests/webadmin_service_tests.cpp` supply unrun parser, real loopback worker, copied-credential revocation and lifecycle fixtures. Owner registration/service/error hooks are now present in `khz_admin_server.cpp`; the upcoming Build54 must include the worker source, test targets and shutdown hook. `sv_webadmin=0` remains the default. Actual engine actions/audit evidence and active 1 kHz load validation are pending. Owner service maximum duration and one-millisecond overrun counts are reported beside HTTP request/completion/rejection/login/timeout counters. No route is marked proven by this document.
